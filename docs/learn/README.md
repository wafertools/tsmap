# Learn tsmap — contributor notes

Learn tsmap is a set of short lessons, one slide deck each, that a new user works through in a
browser. Each lesson ends with a lab in the [web app](https://wafertools.github.io/tsmap/app/)
using the bundled sample data. The published lessons are at
[wafertools.github.io/tsmap/learn](https://wafertools.github.io/tsmap/learn/).

This page is for people writing or updating a lesson.

## How it fits together

| Piece | Where | What it does |
| --- | --- | --- |
| Deck source | `docs/learn/NN-slug.md` | [Marp](https://marp.app/) Markdown, one file per lesson |
| Theme | `docs/learn/theme/tsmap.css` | Matches the docs site and is always light, like the screenshots on the slides; the tsmap icon on title and closing slides and beside every footer except on dividers |
| Screenshot scenario | `scripts/lessons/NN-slug.mjs` | Drives the web build and names every screenshot the deck uses |
| Screenshots | `docs/learn/images/NN/` | Generated by the scenario and committed; never captured by hand |
| Full-screen resume | `scripts/lessons/fullscreen-resume.js` | Added to every built lesson: remembers full screen for the browser tab and re-enters it on the first key press or click in the next lesson |
| Coverage exclusions | `docs/learn/coverage-exclusions.txt` | What is deliberately not taught, with a reason per line |

The scenarios live in `scripts/lessons/` rather than `scripts/scenarios/` because their job is
different: an investigation scenario proves a story works end to end, while a lesson scenario
exists to produce named pictures. Both use the same step vocabulary (`scripts/lib/steps.mjs`) and
the same rules: strict mode, no cosmetic layout changes, and checks that prove the app is on the
screen the beat expects.

## Commands

    npm run demo:build                      # the web app in dist/ (works while wmap is linked)
    npm run lessons:shots                  # every lesson's screenshots
    npm run lessons:shots -- --only 01     # one lesson (or 00,01)
    npm run lessons:shots -- --list        # lessons, beats and screenshot names
    npm run lessons:build                  # decks → site/learn/, with an index page
    npm run lessons:check                  # coverage of the recorded controls

`CHROME_PATH` picks the browser, and `HEADED=1` shows it while a scenario runs.
`lessons:check` needs `../wafermap` checked out beside tsmap to read its controls too.

## Writing a lesson

1. **Copy the pattern.** Start from `scripts/lessons/01-getting-data-in.mjs` and
   `docs/learn/01-getting-data-in.md`. Keep the two-digit lesson number in both names.
2. **Write the scenario first.** Each beat has an `id`, a `title`, `steps`, `checks` and `shots`.
   Run it until every beat passes, then look at every image.
3. **Write the deck around the images.** Then build it and read every slide.
4. **Declare coverage** on each slide that teaches a control, and run `lessons:check`.

### A beat

```js
{
  id: '08-test-selector',
  title: 'Setup ▾ → Tests… opens the test selector on the sample lot',
  steps: [['openTestsDialog']],
  checks: [hasText(SELECTOR, '7 found')],
  shots: [{
    name: 'test-selector',                          // → images/01/test-selector.png
    clip: { target: SELECTOR, pad: 8 },             // crop to an element (optional)
    callouts: [[`${SELECTOR} input[type="search"]`, { badge: 1 }]],
  }],
}
```

- **Steps** are the shared vocabulary in `scripts/lib/steps.mjs`; the index is in
  `scripts/scenarios/README.md`. When nothing fits, add a step there; never work round it in a scenario.
- **Checks** come from `scripts/lib/checks.mjs` (`isVisible`, `hasText`) or are written inline as
  `{ name, describe, get, expect }`. Give every beat that changes the screen at least one.
- **Callouts** are `[selector, options]`. Options: `badge` (a number), `badgeAt` (`tl`, `tr`, `bl`,
  `br`), `pad`, `nth` (pick one of several matches) and `closest` (outline an ancestor). A selector
  that matches nothing, matches more than one element without `nth`, or is hidden stops the run.
- **Clips** take a selector (`target`, with the same `nth`, `closest` and `pad`), an optional
  `maxWidth` to keep the left part of a wide strip, `maxHeight` to keep the top of a tall panel, or a fixed `rect` for a region with no element
  of its own, such as a menu and its button.

When anything fails, the run stops at that beat, names the beat and the step or check, and saves
the page as `demo/lessons/FAILURE-NN-<beat>.png`. A lesson's images only replace
`docs/learn/images/NN/` when every beat has passed.

Screenshots are 1280 × 820 at 2× scale. Prefer a crop to a full screen whenever the point of the
slide is one area: it reads better on the slide and keeps the repository small.

A scenario may set `theme` (a colour theme id, such as `'github-light'`) and its own `viewport`. The runner
stores the theme where the app reads it before the page loads. Every lesson uses GitHub Light at 1280 × 820 and 2× scale (a slide never enlarges an image past its own pixels),
tall enough for a whole Summary panel table in one crop.

### A deck

Front matter:

```yaml
---
marp: true
theme: tsmap
paginate: true
title: "01 · Getting data in"
description: One sentence for the lessons index.
footer: Learn tsmap · 01 Getting data in
---
```

Every deck has, in order: a `title` slide (the lesson number; the index works out the reading time, so the slide gives none), **In this lesson** (up to three objectives), sections
that each open with a `divider` slide, a `lab` slide headed **Try it yourself**, **Recap**, and a
`next` slide. Set a slide's class with `<!-- _class: divider -->`.

- **One idea per slide**, usually one screenshot, and at most about three short lines.
- The `split` class puts up to three bullets beside a screenshot.
- The `side` class is the same for a tall screenshot, such as a menu or a panel: the text sits beside it and it takes the full height of the slide.
- Refer to a numbered callout with `<span class="badge">2</span>`.
- Callout labels place themselves on a free corner of their box; a shot fails when a label has
  nowhere to go, so overlapping labels never reach a slide.
- Lesson 00 defines the terms (die, lot, test, bin, yield) once; later lessons use them without
  explaining them again.
- Give each image alt text that says what it shows.
- Headings must differ within a deck: the docs build turns each into an anchor.
- Link to another lesson as `01-getting-data-in.md` and to a docs page as
  `../user-guide.md#column-mapping-csv-json-and-parquet`. `npm run check:docs` checks both, and
  the build turns them into working links.

### Content rules

- UK English. Describe what the software does now, in a neutral tone.
- Write for end users. Do not dwell on price or licensing.
- Recommend, don't decide: propose a coverage exclusion or a change of scope in review rather
  than making it.
- Source every statement from `docs/user-guide.md`, `docs/features.md`, `docs/ui-surface.txt` or
  the running app. When the guide is silent on something the app does, say so in your notes for
  review rather than guessing.
- Use only the committed synthetic samples in `sample_data/` and `docs/samples/`.
- Labs use the public web app. A sample can be opened straight from a link:
  `https://wafertools.github.io/tsmap/app/?dataUrl=https%3A%2F%2Fwafertools.github.io%2Ftsmap%2Fsamples%2Ftsmap-sample.csv&dataFormat=csv`
  (see [opening data from a URL](../user-guide.md#opening-data-from-a-url)).

## Coverage

`npm run lessons:check` fails while anything a user can reach or read is neither taught by a deck
nor excluded with a reason. It checks two lists:

- **Controls**: every control in `docs/ui-surface.txt` and `../wafermap/docs/ui-surface.txt`.
- **Topics**: every section of the documentation a user reads, named by its document and heading:
  `tsmap guide › Wafer splits` (`docs/user-guide.md`), `wmap guide › Compact layout`
  (wafermap's user guide), `chart › Bin map` (its chart reference) and `glossary › Yield`. A heading
  counts when it has text of its own, so one that only groups others does not.

Topics catch what the control list cannot: a control that only appears in another state (an
overlay of Test Value mode, an option of one chart type) and an idea that is no control at all.
A new section in either guide is reported until a deck teaches it.

A slide declares what it covers in an HTML comment, names separated by semicolons. Controls and
topics go in the same comment:

    <!-- covers: Setup ▾; Setup ▾ › Tests…; tsmap guide › Test selector (STDF and ATDF) -->

A name matches a control's or topic's whole id: a menu or dialog item is written with its parent
(`Splits… › Done`), and `*` is a wildcard. A name that matches nothing is an error, so a renamed
control or heading cannot leave a stale claim behind. The build removes these comments from the
published decks.

Much of the recorded surface is data rather than controls: one finding row, bin chip or wafer chip
for each item in the loaded lot. `coverage-exclusions.txt` folds each such kind of row into one
control (`fold <Name> = <pattern> | <reason>`), and leaves out what is not taught
(`<pattern> | <reason>`). Every line needs a reason and must match something.
