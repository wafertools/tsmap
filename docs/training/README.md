# Training course — contributor notes

The tsmap training course is a set of short slide decks, one per session, that a new user works
through in a browser. Each deck ends with a lab in the [web app](https://wafertools.github.io/tsmap/app/)
using the bundled sample data. The published course is at
[wafertools.github.io/tsmap/training](https://wafertools.github.io/tsmap/training/).

This page is for people writing or updating a session.

## How it fits together

| Piece | Where | What it does |
| --- | --- | --- |
| Deck source | `docs/training/NN-slug.md` | [Marp](https://marp.app/) Markdown, one file per session |
| Theme | `docs/training/theme/tsmap.css` | Matches the docs site, in light and dark; the tsmap icon on title and closing slides and beside every footer except on dividers |
| Screenshot scenario | `scripts/training/NN-slug.mjs` | Drives the web build and names every screenshot the deck uses |
| Screenshots | `docs/training/images/NN/` | Generated by the scenario and committed; never captured by hand |
| Coverage exclusions | `docs/training/coverage-exclusions.txt` | What is deliberately not taught, with a reason per line |

The scenarios live in `scripts/training/` rather than `scripts/scenarios/` because their job is
different: an investigation scenario proves a story works end to end, while a training scenario
exists to produce named pictures. Both use the same step vocabulary (`scripts/lib/steps.mjs`) and
the same rules: strict mode, no cosmetic layout changes, and checks that prove the app is on the
screen the beat expects.

## Commands

    npm run demo:build                      # the web app in dist/ (works while wmap is linked)
    npm run training:shots                  # every session's screenshots
    npm run training:shots -- --only 01     # one session (or 00,01)
    npm run training:shots -- --list        # sessions, beats and screenshot names
    npm run training:build                  # decks → site/training/, with an index page
    npm run training:check                  # coverage of the recorded controls

`CHROME_PATH` picks the browser, and `HEADED=1` shows it while a scenario runs.
`training:check` needs `../wafermap` checked out beside tsmap to read its controls too.

## Writing a session

1. **Copy the pattern.** Start from `scripts/training/01-getting-data-in.mjs` and
   `docs/training/01-getting-data-in.md`. Keep the two-digit session number in both names.
2. **Write the scenario first.** Each beat has an `id`, a `title`, `steps`, `checks` and `shots`.
   Run it until every beat passes, then look at every image.
3. **Write the deck around the images.** Then build it and read every slide in light and dark.
4. **Declare coverage** on each slide that teaches a control, and run `training:check`.

### A beat

```js
{
  id: '08-test-selector',
  title: 'Setup ▾ → Tests… opens the test selector on the sample lot',
  steps: [['openTestsDialog']],
  checks: [hasText(SELECTOR, '7 found')],
  shots: [{
    name: 'test-selector',                          // → images/01/test-selector.png
    clip: { target: SELECTOR, pad: 8 },             // crop to an element (optional)
    callouts: [[`${SELECTOR} input[type="search"]`, { badge: 1 }]],
  }],
}
```

- **Steps** are the shared vocabulary in `scripts/lib/steps.mjs`; the index is in
  `scripts/scenarios/README.md`. When nothing fits, add a step there; never work round it in a scenario.
- **Checks** come from `scripts/lib/checks.mjs` (`isVisible`, `hasText`) or are written inline as
  `{ name, describe, get, expect }`. Give every beat that changes the screen at least one.
- **Callouts** are `[selector, options]`. Options: `badge` (a number), `badgeAt` (`tl`, `tr`, `bl`,
  `br`), `pad`, `nth` (pick one of several matches) and `closest` (outline an ancestor). A selector
  that matches nothing, matches more than one element without `nth`, or is hidden stops the run.
- **Clips** take a selector (`target`, with the same `nth`, `closest` and `pad`), an optional
  `maxWidth` to keep the left part of a wide strip, `maxHeight` to keep the top of a tall panel, or a fixed `rect` for a region with no element
  of its own, such as a menu and its button.

When anything fails, the run stops at that beat, names the beat and the step or check, and saves
the page as `demo/training/FAILURE-NN-<beat>.png`. A session's images only replace
`docs/training/images/NN/` when every beat has passed.

Screenshots are 1280 × 720 at 1.5× scale. Prefer a crop to a full screen whenever the point of the
slide is one area: it reads better on the slide and keeps the repository small.

A scenario may set `theme` (a colour theme id, such as `'github-light'`) and its own `viewport`. The runner
stores the theme where the app reads it before the page loads. Session 03 uses GitHub Light at 1280 × 820 and 2× scale (a slide never enlarges an image past its own pixels),
tall enough for a whole Summary panel table in one crop; sessions 00 to 02 use the default Auto theme.

### A deck

Front matter:

```yaml
---
marp: true
theme: tsmap
paginate: true
title: "01 · Getting data in"
description: One sentence for the course index.
footer: tsmap training · 01 Getting data in
---
```

Every deck has, in order: a `title` slide (the session number, no time estimate), **In this session** (up to three objectives), sections
that each open with a `divider` slide, a `lab` slide headed **Try it yourself**, **Recap**, and a
`next` slide. Set a slide's class with `<!-- _class: divider -->`.

- **One idea per slide**, usually one screenshot, and at most about three short lines.
- The `split` class puts up to three bullets beside a screenshot.
- Refer to a numbered callout with `<span class="badge">2</span>`.
- Callout labels place themselves on a free corner of their box; a shot fails when a label has
  nowhere to go, so overlapping labels never reach a slide.
- Assume the reader is an engineer who knows wafers, dies, bins and yield: recap terms in a line,
  don't teach them.
- Give each image alt text that says what it shows.
- Headings must differ within a deck: the docs build turns each into an anchor.
- Link to another session as `01-getting-data-in.md` and to a docs page as
  `../user-guide.md#column-mapping-csv-json-and-parquet`. `npm run check:docs` checks both, and
  the build turns them into working links.

### Content rules

- UK English. Describe what the software does now, in a neutral tone.
- Write for end users. Do not dwell on price or licensing.
- Recommend, don't decide: propose a coverage exclusion or a change of scope in review rather
  than making it.
- Source every statement from `docs/user-guide.md`, `docs/features.md`, `docs/ui-surface.txt` or
  the running app. When the guide is silent on something the app does, say so in your notes for
  review rather than guessing.
- Use only the committed synthetic samples in `sample_data/` and `docs/samples/`.
- Labs use the public web app. A sample can be opened straight from a link:
  `https://wafertools.github.io/tsmap/app/?dataUrl=https%3A%2F%2Fwafertools.github.io%2Ftsmap%2Fsamples%2Ftsmap-sample.csv&dataFormat=csv`
  (see [opening data from a URL](../user-guide.md#opening-data-from-a-url)).

## Coverage

`npm run training:check` reads every control in `docs/ui-surface.txt` and
`../wafermap/docs/ui-surface.txt` and fails while any is neither covered by a deck nor excluded.
A slide declares what it covers in an HTML comment, names separated by semicolons:

    <!-- covers: Setup ▾; Setup ▾ › Tests… -->

A name matches a control's whole id: a menu or dialog item is written with its parent
(`Splits… › Done`), and `*` is a wildcard. A name that matches nothing is an error, so a renamed
control cannot leave a stale claim behind.

Much of the recorded surface is data rather than controls: one finding row, bin chip or wafer chip
for each item in the loaded lot. `coverage-exclusions.txt` folds each such kind of row into one
control (`fold <Name> = <pattern> | <reason>`), and leaves out what is not taught
(`<pattern> | <reason>`). Every line needs a reason and must match something. Exclusions are
the maintainer's call: propose them, with the reason, rather than adding them.

Not wired into `npm run verify` yet: it fails until every session is written.

What each planned session takes, from the coverage report. Every uncovered control is listed once.

**02 · Reading a map and the toolbar.** The map toolbar: Plot mode (Hard Bin, Soft Bin, Test Value,
and a test), Colour scheme (Default, Colour-blind safe, Use colours from bin definitions), Overlays
(Ring boundaries, Quadrant lines, Die labels, XY indicator, Axis labels, Mark failing dies, Clear
overlays), Legend style (every position), Orientation, Columns. On each wafer: Download PNG, zoom
in and out, zoom to a region, Reset zoom, Pan, Open full view, Expand (E), Reattach to gallery,
Download gallery PNG, the wafer chip, More fields. The dialog frame (Maximize, Close).

**03 · Findings.** The Summary panel: What stands out, finding rows, severity groups and detail
rows, finding chips and chart links, Show supporting findings, Full report ▸, Summary report, Data
tables, and the Wafer Yield (Slot, Yield), Hard Bin Breakdown (Hard, Soft), Ring Yield (Ring,
Quadrant), Test Values and Functional Tests sections.

**04 · The lot view: gallery, stack and splits.** Single wafer, Lot gallery and Lot stack; the
stacked plot modes (Stacked Test Values, Stacked Hard Bins, Stacked Soft Bins); Open and Closed;
Select the same dies on every wafer; Setup ▾ → Splits… and the whole Splits dialog (assign, clear,
save, load, show in labels, split name suggestions).

**05 · Insights.** The Overview, Distributions and Data tabs: Group by (None, Split), Save as PNG,
Expand, Sort, Hard bins, Soft bins, Test limits, Tester flag, Functional; the Test and Wafer menus,
Log scale, Axis includes limits, Clip outliers; Chart actions (Save as PNG, Edit as plot, About this
chart); What divides yield; Part average testing (PAT), Map the verdicts and the PAT verdict plot
mode; Capability, Ppk and the goal plot; Bands on a line; Statistics, Wafers, Dies and the two CSV
exports.

**06 · Correlation.** The Correlation tab: Max tests, the bin chips, Correlation CSV.

**07 · Drilling into any population.** Filter…, Select (drag to select dies), Show on map, the
bin legend's right-click charts, and the Charts and tables menu (Value histogram, Process
capability, Test statistics, Dies).

**08 · Your own plots, derived tests and sweeps.** The Plot tab (+ New plot, + New sweep, Add
examples, Import plots…, Export plots…, Delete all plots…, My plots), the plot editor and its
Customise page (chart types, axes, colour, scales, limits), the sweep editor, New plot… and New
sweep… from a wafer's menu, † Derived tests, Show the sweep ↓, Toggle log scale and the colour bar
range.

**09 · Unusual wafers.** Multi-project wafers (Compact layout, Compact, Layout diagnostics, Reticle
grid, Plot mode → Project); wafers with no positions (Dies without position, View die list);
retests (last, first, best, worst, supersedes); multi-site testing (Hard Bin, Test Site, a site's
fails); reticle overlays (On, Off, Reticle cell) and Setup ▾ → Reticle…; Setup ▾ → Diameter & edge
exclusion…; Setup ▾ → Exclude values outside limits…; the column mapping's Subdivide file.

**10 · Automation and integration.** The command line, opening data from a URL, file
associations; definitions files: Setup ▾ → Bin definitions… (Save…, Load…, recent files), Load bin
definitions… in the column mapping, Help → Definitions file formats…; Help → Reset saved settings…
and About tsmap.
