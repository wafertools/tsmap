# Changelog

For a curated, plain-language summary of what's actually changed for users, see
[What's New](https://wafertools.github.io/whats-new/) instead — this file is the complete
technical record, including internal changes.

## [0.1.33] — 2026-09-02

### Added

- **Eight more colour themes, taking the picker from 8 to 16.** Light gains Gruvbox Light, GitHub Light and Catppuccin Latte; Dark gains Dracula, Tokyo Night, GitHub Dark, Gruvbox Dark and Catppuccin Mocha. They are ordinary token sets in `index.html` behind `[data-theme=…]` and entries in `THEME_GROUPS` (`theme.ts`) — no new mechanism, which is the point: the theme system was already one token vocabulary with the app reading nothing else, so adding an arm is data, not code. The wafer map and its Insights charts follow along for free through wmap's `--wmap-*` bridge rather than keeping a palette of their own.
- **Interface zoom.** **Ctrl** (**Cmd** on macOS) with **+** / **−** scales the entire interface and **Ctrl+0** resets it — `zoomHotkeysEnabled` on the main window plus the `core:webview:allow-set-webview-zoom` capability. Distinct from the wafer map's own zoom, which magnifies the map inside its panel and leaves the chrome alone; this is for a high-DPI display or showing the app to a room. The browser build already had this from the browser itself.
- **Resizable columns in the file filter table.** A drag handle on each heading's trailing edge, modelled as a WAI-ARIA window splitter (`role="separator"` with `aria-valuemin`/`max`/`now`) rather than a button or slider, since that is what it is — focusable, with **Left**/**Right** arrows resizing from the keyboard. Columns also auto-fit their content on each scan, with filenames given the most room (they are what the table exists to compare) and a ceiling so one long path cannot blow a column out to fill the table. A column the user has resized themselves is recorded and skipped by the next auto-fit, so a manual width survives a fresh scan instead of being clobbered. Widths are a per-session display preference and are deliberately **not** written into a saved filter — the same reasoning that already kept hidden columns out of one.
- **Open files and Add files each carry a ▾ offering *Choose files…* or *Scan a folder…*.** Without it the folder picker only existed on the start screen, so once anything was loaded there was no visible way to reach it — and the folder *drop* that partly covered the gap always replaces, never appends, so scanning a folder to **add** was impossible. This is the shape the two-button split was meant to have all along: the verb stays on the button (press it and you get the ordinary file picker, unchanged), and the caret answers the separate question of *how to find the files*. A split button rather than a nested caret, because a click target inside a `<button>` is invalid HTML and unreachable by keyboard — two real buttons, joined visually by a shared seam, with `aria-haspopup`/`aria-expanded` on the caret and the accessible name saying which verb it belongs to. The Add caret follows the Add button's own enabled state at all four places that set it, so it never offers to add to nothing.
- **Scan a folder, instead of picking files twice.** The point is not that a folder is fewer clicks — it is that the two dialogs now ask **different questions**. Before, the OS picker asked *which files* and the triage table asked *which files* again. A folder picker asks *where to look*, which the table cannot answer, so the steps stop overlapping. **Scan a folder…** on the start screen opens a native folder picker; the folder's data files are listed and go straight into the filter table. Backed by a new Rust `list_dir_files` command — extension filtering happens there so a folder of 50,000 unrelated files never crosses the IPC boundary, but the extension list is supplied *by* the frontend (`DATA_FILE_EXTENSIONS`, `lib.ts`) so it stays a single source of truth. A recursive walk is bounded on two axes (depth 3, 5,000 files) because the user can point this at any directory including `/` or a network mount; hitting either cap sets `truncated` and is reported, so a partial listing is never presented as complete. Symlinks are not followed (`file_type()`, not `metadata()`), so a link pointing back up the tree cannot loop. Seven Rust tests cover extension matching including double forms (`.stdf.gz`) and case, the subfolder report, depth truncation, and a *directory* named `lot.csv` not being mistaken for a file.
- **Dropping a folder scans it** — and this was previously broken rather than merely absent: a dropped directory path was wrapped as a `FileHandle` and handed to the parser, which could only fail. It now routes into the same scan, which is also what makes folder scanning reachable once data is loaded, where the start screen is gone. A dropped folder always replaces, matching a dropped file: drag-and-drop has no way to express "append", and inventing one silently would be worse than the Add files button already being there. Dropping folders and files together scans the folders and says so rather than silently picking one interpretation.
- **Subfolders are opt-in, asked once, and only when there are any** — `list_dir_files` reports `hasSubdirs` precisely so the prompt isn't shown for a flat folder. On the web there is nothing to ask: `webkitdirectory` returns the whole subtree by construction, so the prompt is desktop-only.

### Changed

- **The test selector's "Save list" / "Load list" are now "Save definitions" / "Load definitions", and the saved template is `test-definitions-template.csv`.** The file stopped being a list of tests when it gained spec limits, units and test type in 0.1.24 — it defines tests, and "list" invited reading it as selection-only, which is the half of what it does that people already understood. The Lot ▾ entry, the Help → Definitions file formats… dialog and the user guide all use the new wording. **The file format is unchanged**, so anything saved by an older build still loads, `--tests` is unaffected, and a hand-written file needs no edit; only the buttons, the generated template's filename and the docs changed.

- **The three file buttons became two.** Open files, Filter files… and Add files sat in a row as if they were three choices, but they were never siblings: all three funnel into one `handleFiles(files, isAppend)`, and there are only **two** operations (replace, append) against **two** ways of choosing files (the OS picker, the metadata triage table). Open and Add differ on the verb; Filter differed on the picking method and left the verb unanswered — which is why it serialised, ending in "Load selection…"/"Add selection…" and asking again what the toolbar had already asked, in a second vocabulary. `Filter files…` is gone from the toolbar. The table it opened is not: it is now reached by **Scan a folder…**, by dropping a folder, or from Open/Add when the batch is big enough to be worth triaging (`offerFilterFirst`, unchanged) — which is how it was already partly reachable.
- **The filter table has one confirm button, named for the verb already chosen.** `FileFilterHandlers` gained a required `isAppend`, so the dialog is told rather than asking; the two exits collapse to **Load selected…** or **Add selected…**. Making it required rather than optional meant the compiler, not a reviewer, found both call sites.
- **wmap bumped to 0.27.0** (from 0.26.1), a minor bump. It carries three breaking changes and tsmap is affected by **none** of them: `RenderOptions.showMetadataBadge` → `showIdentityHeader` and `setMetadataBadgeVisible` → `setIdentityHeaderVisible` (tsmap never set either — it lets the header default), `HoverTextOptions.waferMeta` removed (never passed), and the `--wmap-bar-fill-muted` theming token removed (never set; tsmap's theme blocks define `--wmap-bar-fill` only). The one change that *did* reach this repo is not an API break at all: the Insights tab's pickers stopped being native `<select>` elements, so the scenario harness had to start driving them by click — see `setInsightsGroupBy` below. Headline additions tsmap gets for free: a per-test pass-rate chart split by group (the chart a split experiment is actually run to produce), a wafer-to-wafer trend chart, split comparison in the lot summary report, population tiles on the Insights Overview, and the `inferred-pitch` advisory downgraded from error to warning — which clears the permanent red banner tsmap's diameter-only wafer-geometry override used to leave on screen with nothing available to dismiss it. Full list in wafermap's own `CHANGELOG.md` [0.27.0]. **Publish, unlink and pin to `^0.27.0` before releasing this.**
- **Every styled button now takes its appearance from one shared class**, enforced by a new `check:buttons` (`scripts/check-button-styles.mjs`, wired into `check:docs`). "The secondary button" had four independent definitions that disagreed on border, colour, padding and size, and only one had a hover state — so half the app's buttons reacted to the pointer and half looked like labels. The classes (`.btn-primary`, `.btn-secondary`, `.btn-icon`, `.btn-chip`, `.btn-link`, `.btn-row`, `.btn-caret`, `.btn-header`, `.tb-btn`, `.menu-row`) live in `index.html`; the call sites set `className` and nothing else. Worth noting how the first version of the checker failed: it read the assignment with `\.style\.cssText\s*=\s*[^;]+;`, which stops at the first semicolon — one *inside* the CSS string — so it inspected a single declaration and passed everything, and it never looked at the object form `el()` takes, which is how `filterTable.ts` and `fileFilterUI.ts` styled their buttons inline the whole time. The scan is now quote-aware and covers both forms.
- **A distinct-value budget on the styling primitives**, `check:styles` (`scripts/check-style-scales.mjs`, also in `check:docs`). It deliberately does not ask "is this value on the scale?" — that is a per-site question a reviewer can answer. It asks how many distinct literals of a kind exist at all, which is the shape every styling defect found in this pass had: four secondary buttons, two tooltip looks, two card frames, three font stacks, eight radii. Each is defensible read alone; the defect exists only in the comparison, which is why reading one file never finds it. Budgets cover `box-shadow`, `transition`, `line-height`, `letter-spacing` and `font-family`; raising one is meant to be a deliberate act recorded in the file.
- **`check:buttons` now also verifies that a button's class actually reaches it.** The original check asked only whether a button *has* a shared class, which is not the same as being styled — and the gap shipped: an ancestor-scoped class used outside its ancestor passed cleanly while rendering as a raw browser button. It now requires every class used on a button to have at least one rule that stands on its own; a descendant-scoped rule layered on top of a base rule is still fine, which is what local tweaks like `.mapping-tools .btn-secondary { white-space: nowrap }` are. Worth recording how the *first* version of this addition failed its own negative test: it parsed selectors without stripping CSS comments, and the comment left behind where `.tool-btn` had been still named `.tool-btn` — enough to register the class as having a base rule. Comments are stripped first now, and the check is verified both ways: it passes the clean tree and fails when the original defect is reintroduced.
- **`check:styles` now enforces the 12px font-size floor.** A distinct-value budget is the wrong instrument for font-size — the question is not how many sizes exist but whether any is too small — so this is a separate flat check over both `font-size:` in CSS/`cssText` and the `fontSize:` style-object form. Also verified in both directions.
- **The theme picker's option list follows the cross-repo option-list contract** now written down in wmap's `UI_STANDARDS.md` — `listbox`/`option` roles, roving `tabIndex = -1` so rows take real DOM focus and the browser draws its own ring, and exactly three visual states (selected, hover, focus) with no hand-drawn focus indicator. Full keyboard support: Arrow keys move, Home/End jump, Enter/Space select, Esc closes, printable keys type-ahead, focus returns to the trigger on close. This is the tsmap half of the convergence in `WMAP_ISSUES.md` #45 — four option-list implementations across the two repos had drifted into three visible styles, reported from the user's side as "the plot mode dropdown, the Lot ▾ menu and the theme dropdown are three different list styles".
- **`scripts/lib/steps.mjs`'s `setInsightsGroupBy` drives wmap's pickers by clicking**, not by assigning `select.value` and dispatching `change`. wmap 0.27.0 replaces the Insights tab's native `<select>` elements with themed trigger-plus-listbox widgets, so there is no `.value` to assign; `data-wmap-select` still marks the same control, now on the trigger button.
- **`src-tauri` stays on rfd's default GTK3 backend**, with the reasoning recorded in `Cargo.toml` rather than left to be rediscovered. Switching to the `xdg-portal` feature visibly fixed a blank-rows rendering glitch in the filter-type dropdown on Ubuntu (isolated with zenity — same theme, same filter names, clean render, so the bug is in rfd's GTK3 combo code, not tsmap or the system theme). Reverted anyway: `xdg-portal` needs libdbus, a portal backend actually installed at runtime, and falls back to shelling out to `zenity` if the portal call fails — none of which is guaranteed on the AppImage's tiling-WM/minimal-desktop audience. GTK3 is already a hard dependency via WebKitGTK, so it imposes nothing extra. Trading a cosmetic dropdown glitch for the file and folder pickers failing outright on some installs is the wrong trade; the blank rows remain a known cosmetic limitation.

### Fixed

- **Shift-clicking in the file filter table selected nothing between the two rows** — it just toggled the row under the pointer, because that table had no range-selection code at all. The test selector and the splits dialog both had it; this one never got it, and nothing in `UI_STANDARDS.md` covered selection, so there was nothing to check the third case against. All three now share `src/listSelection.ts`. The convention is the **checkbox-list** one (Gmail/GitHub shaped, which is what these tables are — a plain click toggles and selection accumulates), not the selection-list one (Finder/Explorer, where a click clears the rest): Shift+Click applies **the anchor's own resulting state** across the range, so shift-clicking after *un*ticking the anchor clears the range rather than selecting it — one gesture serving both directions. The anchor is the last row toggled without Shift and Shift never moves it, so repeated shift-clicks re-extend from the same origin instead of chaining off the previous target.
- **Both existing implementations extended from the wrong row after a filter change.** They stored the anchor as an **index into the visible array**, and nothing reset it when the search box narrowed the list — so clicking a row, typing a search, then shift-clicking extended from whatever row had since moved into that slot. The shared implementation anchors on the row's **ID**, which either still resolves to a shown row or doesn't; "doesn't" is a clean no-anchor case rather than a silently wrong range.
- **Range selection had no keyboard equivalent anywhere** (WCAG 2.1.1 — every mouse gesture needs one). All three lists now support **Shift+↑/↓** (move focus and extend), **Shift+Space** (extend to the focused row without moving focus), plain **↑/↓** (move focus and change *nothing* — focus and selection are separate in the WAI-ARIA APG grid/listbox patterns), and **Ctrl/Cmd+A** (select everything currently shown, matching Select all and the header checkbox, which are also filter-scoped). The handler is scoped to the row checkbox so Ctrl+A never steals select-all from the test selector's inline rename field. 16 tests cover the semantics, including both shift directions, anchor stability, and the stale-anchor case above.
- **The mapping dialog's "Load bin definitions…" button was completely unstyled, and ignored the theme.** `.tool-btn` was only ever defined as `.mapping-tools .tool-btn`, and this one button sits in `.mapping-footer > .pass-bin-group` — so no rule reached it. Measured against its correctly-scoped siblings it rendered with the browser's own `2px outset` bevel, `#efefef` background, `#000` text and 13.3px type: hardcoded values that follow no token, so in all eight dark themes it was a light-grey button with black text, sitting beside a properly-styled Cancel. On the column-mapping dialog every CSV/JSON/Parquet load passes through. The fix removes the class rather than re-scoping it: `.tool-btn` was a **fourth definition of the secondary button** — identical to `.btn-secondary` in background, border, colour, radius, font-size and hover, differing only in padding — so all four call sites now use `.btn-secondary`, and what stays behind is layout only (`white-space: nowrap` for that row, `.tool-sep`). `check:buttons` passed this the whole time because it asked whether a button *has* a shared class, never whether the class *reaches* it; see below.
- **Eight hover hints in dialogs were native `title` attributes** — OS-delayed, unthemed, ignoring overlay stacking, invisible to touch, and forbidden by `UI_STANDARDS.md`, which already records the rule being missed twice. `upgradeTitleTooltips` existed but runs **once at startup over `#toolbar` only**, so it never saw a dialog built later. `splitsUI` (split-name chip) and `filterTable` (header checkbox, sort and filter buttons) now call `attachTooltip` directly; `mappingUI`, whose hints are authored inside a markup template, calls `upgradeTitleTooltips(overlay)` after mount. Both paths strip the attribute as they go, so the slow black OS tooltip cannot also fire, and the text is kept as the accessible name. `filterTable`'s `td.title = cellValue` is deliberately untouched — that is the one permitted use, a fallback for text truncated by CSS.
- **Twelve font sizes below the 12px minimum.** CLAUDE.md sets a flat 12px floor because smaller text renders poorly on Windows WebView2 — a platform none of us develops on, so nothing catches it by eye. Sites were at 10px and 11px across `testSelectorUI` (the limits and type columns, on screen in every STDF load), `fileAssociationsUI`, `splitsUI`, `menuSelect` (the trigger caret and the picker's group headers), `main.ts` (recent-files headings and timestamps) and `index.html` (`.tb-caret`, `.btn-chip`). All raised to 12px, with the couple of `min-width`s that constrained them widened to match. This is a visible change to the affected labels.
- **Enter did nothing in the mapping dialog's "Pass bin(s)" field.** The overlay is not a `<form>` and had no key handler, making it the one text input in the app where Enter was inert — splits, wafer geometry, append-confirm and the test selector all apply on Enter. It now activates **Continue →**.
- **Two validation messages were visible-only.** `waferGeometryUI`'s diameter/exclusion error and `fileFilterUI`'s notice had no `role="alert"`, so to a screen reader Apply simply appeared to do nothing — focus never moves and nothing is spoken. Both now announce, matching `mappingUI`, which already did.
- **The test selector's range box read as a second search field, and its one real rule was invisible.** It sat in its own row directly beneath the search input, styled identically — same border, radius, background and `flex:1` — so two boxes of the same shape sat stacked with opposite verbs: the first *filters the view* as you type, the second *ticks checkboxes* on a button press. Worse, the range is scoped to whatever the search and type filter currently show (every branch guards on the visible set), and nothing said so — searching `vth` then applying `1000-1099` silently selects only the vth tests in that range. The range control now sits in the bulk row beside **Select all** / **Select none**, which have always had exactly that same scoping, so the dialog reads as one row that narrows the list and one row that selects within it — grouped by verb rather than by "is a text input". A range naming nothing shown was also a **silent no-op**: the button appeared dead. Matching is now computed over all tests first and intersected with the visible set second, which is what lets the new inline message tell "no test matches that" apart from "4 are hidden by the current filter — clear it to reach them", and report partial reach ("Selected 2. 2 more match but are hidden"). The message is `role="status"`/`aria-live="polite"`, clears whenever the filter moves so it cannot go stale, and **Enter** in the range box now applies it (stopped from reaching the footer's Import button). The range grammar came out of the closure as an exported, filter-blind `matchTestRange` with 13 tests covering the last-dash split, spaced-dash precedence, list-order name ranges, comma unions and the backwards-range case — it was previously untestable and untested.
- **Saving the file filter produced `filter.json.csv`.** `saveTextFile` (`platform.ts`) hardcoded a CSV/TXT dialog filter from back when test definitions were its only caller, and a native save dialog both constrains and *appends* the offered extension. The filter is now derived from the extension of the name actually being saved.
- **The file dialogs opened unlabelled and identical to each other**, so nothing hinted that the batch-scan path wanted a multi-select — the single most common way to use it wrong, since scanning one file at a time defeats the feature. Both now pass a `title` naming what is expected (desktop only; the browser has no native dialog to title). The file-type dropdown also lists CSV, JSON and Parquet separately instead of as one combined entry, which could not narrow to just one of the three.
- **The theme picker's trigger was the only control in the toolbar that did not match its neighbours.** It hardcoded `background: var(--bg-input)` + `--border-mid` — input chrome — so it rendered as a filled pill in a row of transparent outlined buttons. `makeMenuSelect` now sets no colours at all: it takes `opts.className` and `main.ts` passes `tb-btn`, the same class every other toolbar button uses, so the trigger inherits the shared styling including its accent hover. The caret moved from a hardcoded `--text-muted` to `color: inherit`, or it would stay grey while the label went accent. Verified across all 15 named themes: `#theme-select`'s computed background, border and colour are identical to `filter-files-btn`, `add-btn`, `recent-btn` and `lot-btn` in every one. See `WMAP_ISSUES.md` #45.
- **A cancelled column-resize drag left a live `pointermove` listener attached**, so merely hovering the handle afterwards resized the column from a stale start position, and each subsequent drag stacked another listener on top. `pointercancel` — which fires instead of `pointerup` when the browser takes over a gesture or the pointer leaves the window — now tears down alongside it.

## [0.1.32] — 2026-08-28

### Fixed

- **The in-app user guide ignored dark themes entirely — Nord, Dark, and Solarized Dark all rendered it as plain light**, and worse, wmap's own section of the combined guide (which *does* try to follow the theme) came out with pale, near-illegible text on a plain white background. Verified against Nord and Solarized Dark in the desktop-equivalent (in-page) path: fully correct, seamless theming, no code beyond the removal needed. wmap's own half of this fix (a missing `background` on its guide chrome) ships in wmap 0.26.1.
- **wmap bumped to 0.26.1** (from 0.26.0), patch, no breaking changes. Fixes the guide's dark-theme background (companion to the fix above) and `edgeExcluded` dies rendering almost invisibly against the default light data colour scheme (now a visibly darker, distinct grey). Full list in wafermap's own `CHANGELOG.md` [0.26.1]. Published, unlinked, pinned to `^0.26.1`.

## [0.1.31] — 2026-08-28

### Added

- **Bin definitions**: hard/soft bin names and pass/fail flags, either overriding what STDF/ATDF's own HBR/SBR records supplied or supplying them outright for CSV/JSON/Parquet (which have no HBR/SBR equivalent at all). `packages/parsers` (crate bumped to 0.9.0, published) now parses HBR/SBR (1·40/1·50) — and the WCR record (2·30), see below — from both STDF and ATDF, deduping by bin number the same last-record-wins way a real tester's repeated per-site HBRs need. CSV/JSON/Parquet get definitions via a new **Load bin definitions…** button in the column mapping overlay. Once loaded (any format), **Lot ▾ → Bin definitions…** is a Save/Load-only dialog to view/override them — Load re-renders immediately, since bin names and pass/fail feed `buildWaferMap` directly. Multi-file loads/appends merge bin catalogs across files (`mergeBinDefs`/`mergePassHbins`, `lib.ts`), last file wins per bin number. **Known limitation:** the ATDF field order for WCR/HBR/SBR mirrors the STDF binary layout by assumption — not yet verified against a real ATDF file or the ATDF spec directly; flagged for follow-up if a real sample surfaces a mismatch. Published, unlinked, pinned to `^0.9.0`.
- **Wafer diameter & edge exclusion override**: **Lot ▾ → Diameter & edge exclusion…** overrides wmap's inferred wafer size and adds an edge-exclusion band (dies within it are dropped from yield and shown dimmed). Diameter pre-fills from an STDF/ATDF WCR record when present (real data, trusted over inference) or wmap's own geometric inference (only when it resolved real physical units, never a dimensionless grid-step count). Edge exclusion stays disabled until a diameter is set (live-enforced, not just on Apply) — an absolute mm value is only meaningful relative to a confirmed diameter. Both values persist across restarts and apply to every wafer in whatever's currently loaded. New CLI flags **`--wafer-diameter <mm>`**/**`--edge-exclusion <mm>`** set the same values at launch; `--edge-exclusion` alone still applies on top of a diameter already persisted from a previous session, and is ignored with a logged warning if no diameter is available from either source.
- **STDF/ATDF WCR record parsing** (`packages/parsers`, crate 0.9.0): wafer diameter, die pitch, units, flat/notch orientation, and centre position are now read from the file's own WCR record where present (`lib.ts`'s new `wcrGeometryFrom`, the one place unit conversion and wmap-shape mapping happens) — the same geometry the diameter/edge-exclusion feature above uses as its highest-trust source, and now also feeds `buildWaferMap`'s `dieConfig`/`waferConfig.center`/`notch` directly on every load, not just when the dialog is opened.
- **Long CLI flags accept unambiguous prefixes** (mirroring clap's `infer_long_args`) — e.g. `--edge 3` for `--edge-exclusion 3`. An exact match always wins outright; zero matches is "unrecognized option," more than one is "ambiguous option" naming every candidate. Fixes a latent bug in the same pass: `--h` used to silently resolve to a no-op rather than actually printing help.
- **Help → Definitions file formats…**: reachable with nothing loaded (unlike every Lot ▾ dialog), saves a filled-in example of any of the three definitions-file types (test definitions, splits, bin definitions) via the exact formatter its real Save button uses — discoverable without reading the docs first.
- **wmap bumped to 0.26.0** (from 0.25.0), minor (breaking: die-list `Position` column split into `X`/`Y` — tsmap doesn't render the die list's raw columns directly, so no code change needed here). New in-app report modal (`openReportModal` — Summary/Lot report buttons now open in-page instead of `window.open`, no `setReportOpener` wiring needed), a combined guide "Contents" nav (flat, unnumbered, column-flow — see the Help-menu consolidation below) with a find-in-page search box for the in-page guide fallback, new `Ring`/`Quadrant`/`Edge excluded` die-list columns, `analyzeWaferLot`'s `mixedIdentityFields` (lot identity now requires wafer agreement instead of silently taking the first wafer — closes WMAP_ISSUES.md #30), a CSV formula-injection guard, and a fix for edge exclusion silently misbehaving when it exceeds the wafer radius (closes WMAP_ISSUES.md #42). Full list in wafermap's own `CHANGELOG.md` [0.26.0]. Published, unlinked, pinned to `^0.26.0`.

### Changed

- **Help menu consolidated from two entries to one** ("User guide" — "tsmap guide" and "Wafer map reference" are gone). This reverses issue #32's 2026-07-12 cutover to a standalone guide page (WMAP_ISSUES.md #37, 2026-08-28): wmap's guide window gained a Print/Save-as-PDF button and a controller-free `openWaferMapGuide` export, closing the two gaps that had motivated the standalone page, so tsmap's own guide content is folded back into wmap's combined guide window (`scripts/build-user-guide.mjs` now compiles `docs/user-guide.md` to a generated `src/guideExtension.ts` fragment instead of a standalone `public/guide/index.html` page) — one Help entry point, one guide, regardless of load state.

### Fixed

- **A wmap warning (e.g. a geometry advisory) was re-logged to the log panel every time the view re-rendered for any reason** (a Splits change, the new diameter/edge-exclusion dialog, etc.), not just on the load that first produced it — spamming the panel with duplicates of the same message. Now logged at most once per file load.
- **A declined replace-prompt respawn dropped a just-typed `--wafer-diameter`/`--edge-exclusion`** — `respawn_new_instance` forwarded `--tests`/`--splits` to the new process but not the two new geometry flags.

## [0.1.30] — 2026-08-25

### Changed

- **wmap bumped to 0.25.0** (from 0.24.3), a minor bump with no breaking changes. New additive options: `showLegend` (hide the legend/colorbar), `markFailingDies` (diagonal hatch on failing-bin dies — a non-colour pass/fail channel for colour-vision-deficient viewers and greyscale printing), `perCardLegend` (per-gallery-card legends). ## [0.1.26] — 2026-08-15

### Added

- **Parquet support.** tsmap now opens `.parquet` files alongside STDF/ATDF/CSV/JSON — typed, columnar data through the same column-mapping overlay CSV/JSON already use. Parquet's per-column types (number/bool/string) drive a new `⚠` hint in the mapping table when a numeric-only role (X, Y, a test-value column, …) is mapped to a string-typed column — a check CSV/JSON can't offer, since their cells are untyped text. Native (Tauri) supports every common codec (`snappy`, `gzip`, `lz4`, `brotli`, `zstd`); the web/WASM build supports all of those except `zstd`, whose C library needs a cross-compiler toolchain not assumed to be available wherever the wasm bundle is built — a `zstd`-compressed file parses on desktop and errors clearly on web rather than silently. Row-oriented parsing (no `arrow` dependency), matching this crate's existing row-based model and keeping the wasm bundle small.
- **Open data from a URL, without a human retyping anything.** A caller application can now hand tsmap a URL and have it fetch and load the data itself: `tsmap --url <url> --url-format <stdf|atdf|csv|json|parquet>` on desktop, or `?dataUrl=&dataFormat=` on the web build. This is the programmatic counterpart to the file picker/CLI file paths — not an interactive "type a URL in" dialog. On desktop the fetch (new `reqwest`-based code, tsmap's first network-capable path) happens entirely in Rust *before the window opens*, resolving `--url` to a real local temp file that reaches the frontend indistinguishably from any other CLI file path — so the fetched data reuses the entire existing load pipeline (mapping overlay, test selector, rename, splits) with zero special-casing, and a failed fetch surfaces as an ordinary load error rather than needing its own UI; on the web build it's a direct in-browser `fetch()`, subject to the target server's CORS policy. Desktop also supports `--url-headers <file>` for data APIs that authenticate via a header (e.g. an `Authorization` bearer token) rather than a presigned/self-authenticating link — a small `Header-Name: value`-per-line file, mirroring `--tests`/`--splits`, so the secret never sits on the command line itself. The web build has no equivalent (a header-based secret has nowhere safe to live in a page URL) and still requires a self-authenticating URL. See the guide's new "Opening data from a URL" section.
- **File associations.** A new **Help → File associations…** dialog (desktop only) lets you opt in/out of tsmap being the default handler for `.stdf`/`.atdf`/`.parquet` files, so double-clicking one in a file manager opens it in tsmap — deliberately excludes `.csv`/`.json`, which are already claimed by too many other apps to safely default to. This is an in-app setting rather than an installer option, so it can be changed anytime without reinstalling: a Windows installer can offer per-item checkboxes, but there's no equivalent for a `.deb`/`.rpm`/AppImage install on Linux, so an installer-only mechanism would have been Windows-only. Implemented via the Windows registry (`HKEY_CURRENT_USER\Software\Classes`) and Linux's `xdg-mime`/shared-mime-info/`mimeapps.list`; a restricted/locked-down machine (registry or config-directory write access denied by IT policy) surfaces a clear inline error rather than silently failing. Each row also shows the executable path currently registered for that file type (or that would be registered, if unchecked) — the path the OS will actually launch on a cold double-click, which can silently drift from the tsmap you're currently running (e.g. an association last turned on from a development build); a mismatch is flagged inline instead of surfacing later as a launch failure.
- **`tsmap://` URL scheme (deep link).** A web page can now launch the desktop app directly with `<a href="tsmap://open?url=<data url>&format=<format>">` — the desktop counterpart to the `?dataUrl=` web-build query param, for callers whose users are on the desktop app rather than (or as well as) the browser build. Via `tauri-plugin-deep-link`; on Linux/Windows the OS relaunches tsmap with the link as a plain CLI argument, so it flows through the exact same `--url`/`--url-format` resolution and single-instance forwarding already in place — no new IPC or frontend code. ## [0.1.25] — 2026-08-09

CSV/JSON test numbers are now stable across reordering (2026-08-09), a follow-up to
M7 below: duplicate-role validation stopped two columns silently sharing a number,
but the underlying numbers were still fragile in a different way.

### Changed

- **CSV/JSON test numbers no longer depend on column or row order.** They used to be assigned `1001, 1002, …` — for wide format, in the order columns appeared in the mapping table; for long format, in the order test names were first encountered while scanning rows. Either one meant re-parsing the same logical test set after a column was added/removed/reordered, or after a file was re-exported in a different row order, silently renumbered every test — invalidating any saved test list or override keyed by number, with no warning. Numbers are now a deterministic hash of the test's own identity (the source column for wide format, the test name for long format — see `stableTestNumber` in `lib.ts` and its independent Rust mirror in `testdata-parser`'s new `test_identity.rs`), collision-probed so two different tests in one file can never land on the same number. Real STDF/ATDF test numbers are untouched — this only affects the two formats that never had a real test number to begin with.
- **A new `order` field, independent of the number, drives display order.** The test selector used to sort by test number, which happened to equal file order only because numbers were assigned in file order — a coincidence this change would otherwise have broken, since a hashed number has no relationship to where its column sits. `order` (column position for wide format, first-encounter order for long format; absent for STDF/ATDF, where sorting by the real number is still correct) now carries that instead, so tests still list in the file's own order despite the number itself being an arbitrary large integer.
- **Loading a saved test list now recovers a stale number by matching on name.** If a row's saved number isn't in the current scan, its name is checked against the current tests before giving up — this is what makes a saved list, or a list a user hand-edited, survive the numbering scheme changing (or any other renumbering) without needing to know why the number went stale. A name matching more than one current test is never guessed; it's counted and reported separately from a genuinely-unknown test. The load summary now distinguishes three outcomes instead of two: matched by number (silent, as before), recovered by name (new — an info-level note suggesting the list be re-saved), and not found (unchanged). `docs/user-guide.md`'s Test lists section, which documented the old two-outcome "silently skipped" behaviour outright, is updated to match.

### Internal

- The wide-format numbering fix lives in TS (`mappingUI.ts`'s `readMapping` — wide-format numbers are assigned there, before the mapping ever reaches Rust); the long-format fix is duplicated in Rust across `parse_csv.rs` and `parse_json.rs`, which have always had separate, near-identical long-format pivot logic. The two hashing implementations don't need to agree numerically — TS's wide-format numbers and Rust's long-format numbers are computed independently and never compared — but Rust's long-format pass seeds its collision set with whatever wide-format numbers the same mapping already assigned, so the two schemes can't collide within one file even when a mapping combines both (the mapping UI allows this: some columns "Test value", others "Test name"/"Test result").
- The stale-number recovery logic was extracted into a pure, exported `resolveLoadedTestList` (`testSelectorUI.ts`) rather than left inline in the DOM-driven load handler, so it has direct unit test coverage instead of only being reachable through the full overlay.
- Verified end-to-end through the real WASM path, not just `cargo test`: the parsers crate has no local-link workflow for the web build (see this file's "Shared parsers crate" section), so a local `wasm-pack build` was temporarily swapped into `node_modules` to confirm the hash survives the actual browser-facing boundary, then reverted — the published `@wafertools/testdata-parser` package is unchanged on disk. **The crate version must still be bumped and published before any release**, per the existing rule; nothing here does that automatically.

### Fixed

- **A long-format CSV/JSON with a `test_val`-style value column silently collapsed to one test.** `detectRole`'s auto-detection only matched the exact strings `test_value`/`val`/`meas_val`/etc. for the "Test result (long format)" role — a real-world column literally named `test_val` (the bundled `testdata/correlated_long.csv` fixture; presumably not unique to it) matched none of them and fell through to the numeric-fallback heuristic, which classified it as a single ordinary wide-format "Test value" column instead. With `testvalueCol` then unset, the file silently parsed as wide-format with that one bogus column — no error, no warning, ~30 real tests reduced to 1. Added regex fallbacks for both `testname` and `testvalue` (mirroring the existing `loLimit`/`hiLimit`/`units` regex patterns, added for the identical reason: an exact-string list doesn't scale to every real header spelling). Verified against the actual fixture end-to-end: all 30 tests now load. The guide's column-mapping screenshot was captured against the same fixture and silently documented the bug (`test_val` shown mapped to plain "Test value") — recaptured.
- **"Add files" followed by cancelling the column-mapping overlay left a permanently blank window.** `showMappingOverlay` cleared `#map-container` as a side effect of opening, on the assumption it only ever ran before anything was rendered. `handleFiles()` is the shared path for both *Open file* and *Add files*, so appending a CSV to an existing gallery wiped that gallery the moment the overlay appeared — and cancelling restored nothing, leaving the app showing an empty view while still holding the wafers (Add, Splits and Filter tests all stayed enabled). The clear also bypassed `destroyMainView()`, leaking wmap's controller and observers. Clearing the view belongs to `handleFiles`, which does it via `showLoadingState()` only after the cancellable gates resolve; the overlay no longer touches the container at all.
- **Resizing the window permanently retitled the app to an error string.** A module-load debug handler in `index.html` rewrote `document.title` on *any* window error event, and wmap's `ResizeObserver` emits the benign "ResizeObserver loop completed with undelivered notifications" notice during an ordinary resize. The title then stayed `ERR: …` for the rest of the session — the browser tab on web, the OS window title and taskbar entry on desktop, reading as a crash. The handler now fires only for genuine script errors (an error with a source file) and only before the app has booted.
- **wmap's Summary panel rendered near-invisible dark-on-dark text on every dark theme (Dark, Nord, Solarized Dark).** wmap reads its chrome colours from 26 `--wmap-*` custom properties (`WMAP_TOKEN_NAMES` in its own source); tsmap's `:root` block mapped only 20 of them to tsmap's own tokens. The other 6 aren't unstyled when unmapped — wmap falls back to its own hardcoded *light-theme* defaults, because that's what keeps the library usable in a host that sets no theme at all. The one that actually bit: `--wmap-text-strong` (wmap's `CLR.value`, used for the Summary panel's headings and big stat numbers) fell back to `#1f2f43` — near-black — landing on a near-black panel background at under 1.1:1 contrast on every dark theme. `--wmap-err-bg`/`--wmap-err-border`/`--wmap-err-text` and `--wmap-finding-indicator` had the identical gap, just not yet exercised by anything visible in normal use. All six are now mapped; `--wmap-z` is the one token left deliberately unmapped, since tsmap's own z-index scale is defined *above* it on purpose rather than substituted for it.
- **The toolbar pushed the theme picker and Help button off-screen below ~900px**, with no wrap and no overflow, so they could not be scrolled to or revealed. The decorative "or drop a file anywhere" hint now drops out at ≤1100px and the title at ≤700px, and the bar scrolls horizontally as a hard floor. Measured: the right-hand group is reachable at every width down to 640px.
- **The column-mapping Role dropdowns were indistinguishable from text inputs.** `appearance: none` removed the native arrow with no replacement, leaving them pixel-identical to the real text inputs in the adjacent *Test name* column. They now draw a caret (built from gradients rather than an SVG data URI, so it follows the theme).
- **The test selector's memory advisory was never themed.** It read `var(--error, …)` and `var(--warn, …)`; neither token has ever existed (the themes define `--error-text`/`--warn-text`), so all eight themes fell through to hardcoded hex — putting `#fbbf24` amber on High contrast's white ground at about 1.9:1.
- **Column mapping silently accepted duplicate roles.** Two columns set to the same single-valued role (X, Y, wafer, lot, bin, …) resolved by last-one-wins overwrite, discarding the first with no feedback and producing a plausible-looking map built from the wrong column. Now blocked before parsing, with a message naming every clash.
- **"Filter tests…" dropped the memory advisory and the themed confirm.** Both were passed only on the initial load — backwards, since this is the path that can *widen* a selection and force a re-parse. The prompts also fell back to a bare `window.confirm` on this path while using the native themed dialog on the other.
- **The rename overlay and append confirmation had no keyboard exit.** Neither responded to Escape, the rename overlay had no initial focus and ignored Enter, and the append confirmation had no backdrop-click, `role="dialog"` or `aria-modal` — the only two dialogs in the app without any of it. The append confirmation now goes through the shared `openModal`; the rename overlay commits on Enter, cancels on Escape and focuses its first field.
- **Append warnings could print the literal string "undefined"** for a file with no hard-bin column (`hbin` is optional and landed in the bin set), and the "Wafer grid size differs" check only ever compared the X span, so a differing row count passed silently.
- **The primary button failed WCAG AA in four themes.** White on `--btn-primary-bg` measured 2.5:1 in Light green, 3.4:1 in Solarized Dark, 3.7:1 in Solarized Light and 4.0:1 in Nord. A new `--btn-primary-text` token lets Light green use dark ink on its bright brand green (6.5:1) instead of forcing the green darker; Nord and both Solarized themes take their button ground two steps down the same hue (5.1–6.2:1), with `--accent` left at each palette's exact published value so links and active chrome are unchanged.
- **Nord's and Solarized Dark's `--error-text` failed AA against their own app background** (3.05:1 and 3.25:1 respectively) — found while wiring up the new `--wmap-err-*` mapping above, since that reuses `--error-text` and would otherwise have carried the same failure into wmap's own error banner. New `--error-bg`/`--error-border` tokens were added to all eight themes to pair with `--error-text`, mirroring the existing `--warn-bg`/`--warn-border`/`--warn-text` triad.

- **Guide screenshots displayed at up to double their real size, and squashed out of aspect ratio once wider than the reading column** — every screenshot is captured at `deviceScaleFactor: 2` for crisp text, but nothing told the browser that, so images rendered at their raw (2x) pixel size; and once explicit `width`/`height` were added to fix that, wide images lost their aspect ratio under `max-width: 100%` because `height` stayed pinned to its literal attribute value.
